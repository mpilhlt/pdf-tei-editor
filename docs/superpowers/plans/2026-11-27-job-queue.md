# Job Queue for Long Server Processes (Core) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run every long server process of the core through fastapi-jobqueue, started, followed and cancelled through one client API, with the progress widget driven by the job event stream.

**Architecture:** Core mounts a `JobManager` (SQLite store shared by the 4 workers) at `/api/v1/jobs`, with auth from the editor's sessions, file locks as job resources, and a `job_type()` registry for core and backend plugins. The frontend gets a pure `JobClient` module and a `jobs` plugin that keeps one event stream for all of the user's jobs and renders each job as a progress widget. OCR, the OCR LLM correction, text corrections, the OCR LLM review, extraction and backup are migrated; an admin job list comes last.

**Tech Stack:** FastAPI, fastapi-jobqueue (`~/Code/fastapi-jobqueue`, github.com/cboulanger/fastapi-jobqueue), Pydantic v2, vanilla JS plugins (JSDoc-typed), Shoelace, Playwright E2E, Python `unittest` runner, Node test runner.

**Spec:** GitHub issue mpilhlt/pdf-tei-editor#961 and its decisions comment (`gh issue view 961 --comments`). Library spec: cboulanger/fastapi-jobqueue#1; library README: `~/Code/fastapi-jobqueue/README.md`.

## Review Focus

1. **Cancel handled by another worker.** A cancel `POST` reaching a worker other than the one running the job must stop the job (the old in-memory token bug). Pinned by the store-backed cancel test in Task 2 and the E2E cancel in Task 5.
2. **Reload during a running job.** After a page reload, the widget of a running server job reappears and its result is still delivered. Pinned by the reload E2E in Task 5.
3. **Two submits for the same PDF** (two tabs, double click): the second gets 409 with a readable message, not a second OCR run. Pinned in Task 6.
4. **Locks outlive 90 s.** A job holding `file:<id>` longer than `LOCK_TIMEOUT_SECONDS` (90) keeps the lock (renew hook) and releases it on done, error and cancel. Pinned in Task 2.
5. **Event stream drops.** `JobClient.wait()` still settles when the stream is down (reconnect with `Last-Event-ID`, polling fallback). Pinned in Task 4.
